# Review audit — PR #212, the key migration and rotation design

Date: 2026-09-07
Reviewer: Codex (automated, one round)
Reviewed commit: 22a8210
Outcome: 7 accepted and fixed in db4be41, 2 rejected

Written because two of the nine findings were **rejected**. `CLAUDE.md` asks for an
audit only in that case; the seven accepted findings are recorded by the PR thread and
by the commit that fixed them, and are summarised here only so the rejections have
context.

The review was one round, automated, against commit `22a8210` — a commit containing
nothing but `docs/plans/2026-09-07-key-migration-and-rotation-design.md` and the ledger
and progress entries for item 23. Every finding is therefore about a design, not about
running code.

## Accepted — seven

All seven were real, all were in the two categories that matter most for this product:
a design that would have lost words, and a design that would have left a revoked
credential working. Fixed in `db4be41`.

| Finding | The gap |
|---|---|
| Derive a 32-byte KEK | `ARGON2_PARAMS.hashLength` is 64. A literal implementation would have failed `importKey` before wrapping one account. |
| Invalidate remembered keys after a passphrase change | `K` is unchanged, so a stale stored key *would* still decrypt the new key-check. Decryption cannot be the test; the stored `keyCheckVersion` must be. |
| Revoke the legacy passphrase when changing it | An old client derives from `encryption_salt` and unlocks with the retired passphrase. A revocation that did not happen. |
| Persist a recoverable `K_new` before rotating rows | A dead tab took the only copy of a random key with it; the rows already rewritten were unrecoverable. |
| Pause rotation writes across every device | `pauseSync()` is module-local to one tab. A second device would have pulled an already-rotated row and, because reads fail closed, emptied its own library. |
| Lock concurrent rotations before the first batch | `wrapVersion` does not advance until the pass ends, so both rotations read an unmoved version and both proceed. |
| Use compare-and-set for concurrent passphrase changes | Both writers read back their own bytes and both report success. Only one passphrase is live. |

The corrections keep the wrong reasoning next to the right one rather than deleting it —
these are the mistakes the next reader is most likely to make again, and a design that
shows only its conclusions cannot warn anyone.

Two are worth naming as more than fixes. `pendingWrap` (§2.3 step 3) is the difference
between a resumable rotation and permanent data loss, and the design as reviewed
*promised* a cursor resume it could not deliver. And the server-side gate (§2.3 step 2)
is the point at which this stops being a single-device design; the reviewed draft said
"sync is paused" and meant one tab's flag.

## Rejected — two

### 1. "Mark the completed design with the shipped-plan lifecycle"

> This commit removes item 23 from the active ledger and records it in `docs/progress.md`
> as completed, but its artifact remains `Status: PROPOSAL` in the live plans directory.

**Rejected.** Two different things are being conflated: the *item* and the *design*.

Item 23 is "write the design". That shipped. `docs/progress.md` records it, correctly.

The design describes work — items 24, 25, 26 and 103 — that has not been built. Its
`Status:` header tracks the design, which is what a reader opening the file needs to
know. Flipping it to `COMPLETE` would tell that reader the wrapped master key exists.
It does not.

The lifecycle rule the finding cites — *work ships → COMPLETE, move to `docs/archive/`* —
would, applied here, archive the specification that four open ledger items are supposed
to be built from, into a directory `CLAUDE.md` describes as frozen, unindexed, excluded
from default search, and "not authoritative for anything". That is not a lifecycle
violation avoided; it is the document destroyed by process.

The plan says all of this at the top, in a paragraph headed **On the status line**,
added before the review ran. It flips to ACTIVE when someone picks up item 24.

### 2. "Add the required product changelog entry"

> The new progress entry declares item 23 shipped, but this commit does not add the
> corresponding `src/data/changelog.ts` entry required for significant changes.

**Rejected.** `CLAUDE.md` says of the changelog: *"that is a product surface (release
notes rendered in the app), not documentation."* It is read by people who use Yidhan,
inside Yidhan, to find out what changed for them.

Nothing changed for them. Item 23 added a document to the repository. There is no
feature, no fix, and no behaviour to describe; a line saying so would be an entry about
the development process shown to someone who wanted to know what is different about
their notes app.

This PR does carry a changelog block (3.19.15) — six lines, for items 36, 38, 39, 40 and
41, every one of which a reader can see. The absence of a seventh for item 23 is the
rule being applied, not skipped.

## What this round did not cover

The reviewed commit was the design alone. Items 36, 38, 39, 40 and 41 — the code, the
migration, the backup format, the security page — landed in later commits and were not
re-reviewed; one round per PR is the agreed cost. The seven fixes above are also
unreviewed, being the response to the round.

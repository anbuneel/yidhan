## Recommendation

Build Yidhan around a complete journey: capture a thought quickly, find it later, develop it into finished writing, and trust that it remains private and recoverable across devices.

The visual identity and technical foundations are credible. The largest remaining opportunity is dependable interaction: precise saving states, safe recovery, consistent browser behavior, and tools that let a short note grow into a longer document. Those improvements should precede expansion into publishing, AI reflection, or team workspaces.

Retain the browser-first React/Tiptap/Dexie/Supabase architecture. There is no evidence from this review that a framework rewrite or early native rewrite would produce more value than strengthening its contracts.

## First release: trust the latest words

### Save state must describe durable state

The editor waits for an encrypted local write before reporting save success, which is good. However, “Saved” is also used for the later pending-to-synced transition. The distinction between saved on this device and synchronized needs to remain understandable.

Source review also found a concrete inconsistency: performSave returns false on failure; the search shortcut checks that result, while Escape and the logo navigation await the save and then navigate regardless. A failed save message returns to idle after five seconds and sits in a header hidden by focus mode.

Make every exit path respect failed persistence. Preserve the in-memory draft, keep a small actionable failure state visible even in focus mode, and offer Retry, Copy, or Export. Do not imply another device has the latest text before the server confirms that revision.

The existing 800 ms inactivity debounce and visibility/pagehide flush are helpful, but continuous typing needs a bounded maximum persistence interval. Browser termination cannot be made safe by relying on an asynchronous exit handler alone. Persist encrypted draft checkpoints during editing and verify precisely which revision the UI has acknowledged.

Sources: src/components/Editor.tsx:356, :411, :431, :505, :541, :680, :1125; src/App.tsx:1319.

### Add encrypted revision history and independent recovery

The current offline database has notes, tags, links, a sync queue, conflicts, and hydration metadata. It has no retained per-note revision store. Normal update compaction replaces earlier pending updates, so the sync queue is not revision history. Faded Notes protects deleted notes, not an accidentally replaced paragraph.

Add a bounded encrypted revision journal, session checkpoints, preview/restore/save-as-copy, and recoverable snapshots before conflict resolution. Sync retained encrypted revisions if recovery should survive a lost browser/device. Define retention and deletion behavior explicitly.

Add an encrypted downloadable backup that can be restored in a fresh browser. Include note identity, timestamps, tags, attachments, and revision metadata as the model grows. Test restoration; a successful download is not proof of a usable backup. Browser persistence reduces eviction risk but does not protect against explicit site-data clearing or device loss.

Sources: src/lib/offlineDb.ts:140, src/services/encryptedNotes.ts:241; [merged storage fix](https://github.com/anbuneel/yidhan/commit/c7b6bbeac80884950e15910c28000d6014cbb580), [StorageManager persistence behavior](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/persist).

### Make concurrent updates safe at the server

The update path reads the server row, checks timestamps/content hashes, and later updates by note ID. That leaves a window between checking and writing in which another device can write. The synchronization guard is module-local and does not coordinate separate tabs.

Introduce a server-enforced revision precondition and idempotent mutation identity; serialize queue ownership across tabs with a recoverable lease or supported browser locking mechanism. Keep the existing local note-plus-outbox transaction. Preserve both conflicting revisions and offer a calm recovery flow. A general collaborative CRDT system is a separate decision, not a prerequisite for safe personal multi-device use.

This is a source-supported concurrency risk, not a reproduced production overwrite.

Source: src/services/syncEngine.ts:81 and :575–645.

### Isolate damaged records without hiding them

fetchDecryptedNotes already avoids silently returning a partial library: one failed decryption throws, and the caller clears the visible notes and displays a toast. Keep the fail-closed handling of the affected payload, but avoid making one damaged record render every healthy note unavailable.

Represent an unreadable item explicitly, preserve its ciphertext, show a persistent incomplete-library state, and allow verified healthy notes to remain accessible. Exports must explicitly report incomplete results or block a “complete backup” claim. Never drop unreadable notes silently.

Sources: src/services/encryptedNotes.ts:284 and src/App.tsx:816.

## Privacy needs to cover the entire journey

Define the product promise as provider-blind personal content with explicit limits for operational metadata, the browser/device, and the code delivered to it.

1. **Correct the practice-space promise.** Its starter note currently says notes are end-to-end encrypted, but the demo stores complete JSON in localStorage. Landing drafts also store plaintext. The demo is useful; label its actual state clearly and retain the context inside the editor. The privacy promise must apply to the current draft, not only the future account.
2. **Protect incoming capture.** The manifest uses a GET share target; title/text/URL arrive in query parameters, and the hook stages them as plaintext in localStorage. Remove private captured text from navigation URLs. A locally intercepted POST workflow requires a defined service-worker, locked-vault, failure, and fallback design; switching to a server-handled POST alone would not deliver provider-blind capture.
3. **Encrypt semantic metadata.** Tags are currently plaintext and documented as such. Tags can reveal sensitive topics. Encrypt tag names and future collection names, attachment names, previews, and link metadata where possible; build retrieval indexes locally. State which routing, timing, and size metadata remains visible.
4. **Add usable recovery and key rotation.** Setup explicitly says there are no recovery codes. A user-held recovery kit can preserve E2EE without giving Yidhan a decryption key. Separate a random vault key from the passphrase wrapper so changing a passphrase need not always re-encrypt every note. Treat compromise rotation, remembered devices, old offline devices, and restoring backups as a versioned migration project.
5. **Review browser key persistence and all outbound data.** Remembered keys are an opt-in localStorage convenience. Model the associated device/XSS exposure and make the UX honest. Preserve the restrictive CSP and self-hosted assets; use allowlisted diagnostic fields and audit full URLs, demo/capture paths, attachments, and error strings.
6. **Commission an independent security review** before making broad public assurances. Include migrations, auth, account deletion, sharing, recovery, and delivery-chain trust as well as the encryption primitive.

## Next release: a note can become finished writing

Prioritize an optional heading outline, find/replace within a note, word/character count, heading folding, simple tables, and footnotes. Preserve selection, native undo, IME composition, paste fidelity, and mobile keyboard behavior. Offer readable PDF/print output and dependable Markdown export; add DOCX when target writers need it.

Use one document-command model for the sidebar, full toolbar, mobile toolbar, slash menu, and keyboard shortcuts. Every width should provide access to the same capabilities through appropriate grouping and overflow.

The current Tiptap extension set supports core formatting, task lists, and slash commands, but has no explicit table, attachment, outline, footnote, or internal-note-link model. HTML is serialized on every edit. A versioned structured document format would become useful as richer nodes arrive, but migrate incrementally and keep HTML rendering/export compatibility. Avoid replacing the editor solely for architectural tidiness.

## Capture, retrieval, and migration

- **Capture:** make Start writing reach an editable draft in one action on both desktop and mobile. Add a stable private new-note URL, installable shortcuts where supported, and append-to-existing-note capture. A browser clipper can follow once its permission and encrypted-staging design is clear.
- **Retrieval:** retain temporal chapters for browsing; add a fast note switcher, ranked title/body search, phrase/date/tag filters, snippets, keyboard selection, and saved searches. Search currently filters already-decrypted notes; it does not need a speculative “stop decrypting every keystroke” fix from an older issue.
- **Connections:** add stable private note URLs and simple internal links/backlinks. Offer lightweight named collections or saved views without making a permanent sidebar mandatory. Test the need for one primary organization model before adding both deep folders and elaborate tags.
- **Scale:** current search reparses note HTML and scans every candidate; search renders all matching cards, bypassing progressive rendering. Cache normalized search text, use a local worker/index, keep derived indexes encrypted at rest or memory-only while unlocked, and virtualize large result sets.
- **Attachments:** begin with pasted/dropped images and PDFs, then local OCR where practical. Encrypt originals, filenames, thumbnails, extracted text, and attachment manifests before upload. Include resumable transfer, offline availability, quota handling, cleanup, and export. A plain storage upload button is not a complete attachment feature.
- **Migration:** provide previewed imports from the formats people actually have: Markdown folders/ZIPs, Bear/TextBundle, Notion exports, and supported Apple Notes export workflows. Explain unsupported formatting/media before import and provide counts and reconciliation afterward. Existing Markdown conversion uses sequential regular expressions and the bulk Markdown export creates one combined file; richer round trips merit a real parser/serializer and fixture-based verification.

### Design specificity verdict

The interface feels authored for Yidhan. Its visual vocabulary is coherent rather than interchangeable. The six-file static detector returned zero findings, but did not detect the privacy-copy mismatch or the interaction concerns. A zero static result is not an endorsement of the entire UX.

### Five priority issues

1. **P1: precise privacy and storage language.** Clearly separate unencrypted practice drafts, locally saved encrypted notes, and synchronized revisions. Use plain labels at trust-sensitive moments. Suggested work: clarify/harden.
2. **P1: actionable failure status.** Retain failed-saving state until resolved, including in focus mode, with Retry and Copy/Export. Suggested work: harden.
3. **P2: responsive command consistency.** At 1100 px and wider, CSS hides the full inline toolbar while the sidebar supplies a subset. On a narrow mouse-driven viewport, the full toolbar remains and occupies three rows. Choose composition by available space and gestures by input capability. Suggested work: adapt.
4. **P2: preserve readable words.** A permanent 48 px mask fades even short card previews. Enable a continuation cue only for actual overflow; retain strong text contrast for older notes instead of fading semantic content with age. Suggested work: polish.
5. **P2: consistent capture and browser navigation.** The desktop landing opens a writing surface; mobile routes to the demo library. Make the first action immediately useful and add a coherent note-URL/Back/Forward contract. Existing authenticated navigation persistence should be preserved. Suggested work: adapt.

### Personas, cognitive load, and emotional journey

The reflective writer benefits from calm surfaces but needs truthful reassurance when writing private material. The frequent writer benefits from focus and shortcuts but encounters inconsistent formatting access. The first-time mobile visitor needs fewer steps between Start writing and an editable draft. A keyboard/screen-reader user needs verified editor labeling, status announcements, focus order, and modal behavior; accessible names in an AX tree are only preliminary evidence.

The interface generally has low visual competition. The wide toolbar's action count is not inherently a problem when grouped sensibly. Recognition and consistent disclosure matter more than removing commands.

The emotional high point is the landing becoming an editable page and the quiet focus view. The vulnerable point is interruption or uncertain saving. End each session with a clear, accurate indication that the latest words are retained.

Minor observations: some narrow-layout hit targets measured below the project's 44 px touch target preference, but hit-area exceptions were not assessed and no WCAG failure is claimed. Metadata and navigation could be more legible. Long titles, dense tags, RTL, Tamil/CJK input, screen zoom, and real virtual keyboards need dedicated task testing.

## Browser-first quality gates

Run the core journeys on Chrome, Edge, Firefox, and Safari, and on real iPhone/iPad and Android devices. Automated WebKit helps but does not replace actual iOS keyboard and installed-PWA testing.

The current main E2E configuration defines Desktop Chrome and Mobile Chrome; authenticated tests depend on credentials and can skip. CI runs unit/coverage and a real production service-worker update suite, which is valuable, but not the main authenticated browser journey suite. Some older E2E expectations still describe superseded behavior (for example, non-expiring sharing).

Add an isolated test-account/environment fixture that can authenticate and unlock the vault. Cover:
- Write continuously, interrupt, reload, reopen, and recover the latest acknowledged revision.
- Edit the same note on two devices and two tabs, including one offline.
- Network flaps, expired auth, rejected local writes, quota pressure, denied persistence, and blocked mutations.
- Upgrade an open installed PWA with dirty work and lazy chunks.
- Import, export, and restore with nested formatting, Unicode, attachments, and links.
- Lock, sign out, rotate/recover keys, and return from an older offline device.
- Account deletion with the existing verified rollout gates, not a casually re-enabled feature.

Recommended initial targets, to be measured on a defined test device and dataset:
- Already-unlocked warm launch to editable note: p95 under 1 second.
- Typing responsiveness: p95 below 100 ms for an agreed long-document fixture.
- Bounded local checkpointing during continuous typing; never acknowledge a revision before its encrypted write commits.
- Search: p95 below 200 ms at 10,000 representative notes after indexing.
- Healthy-network cross-device visibility: p95 below 5 seconds after local persistence.
- Recovery: zero lost acknowledged edits in fault-injection runs, and a complete backup restored successfully into a fresh profile.

These are proposed acceptance criteria, not measured current results or guarantees against device destruction.

## Sustainable implementation

Extract responsibilities when touching them: document persistence, note lifecycle, search, attachments, and vault lifecycle should have clear interfaces. App.tsx is 2,662 lines and Editor.tsx is 1,535 lines; their coupled state makes lifecycle changes harder to reason about. Module size alone is not a defect, but growing feature breadth in these files increases change risk.

Prioritize actual work on the input path: HTML serialization/parsing, KDF work, library decryption, unnecessary rendering, and route loading. Dynamic imports do not help when the same module remains statically imported; the build reports several examples. Preserve offline assets and font licenses when optimizing load cost.

Automate migration ordering, drift verification, and deployment compatibility. A user should not need to diagnose whether the app shipped ahead of a required database change.

For a sustainable private service, test willingness to pay for the polished core before making unlimited encrypted attachment or backup promises. Model storage, transfer, retention, support, and independent review costs. Avoid funding assumptions that depend on analyzing private content.

## Sequence

| Release | Outcome | Principal work |
|---|---|---|
| 1: trust the notebook | Latest words remain private, durable, visible, and recoverable | Save/exit fixes, server write preconditions, revision recovery, capture/privacy cleanup, backup restore, core browser journeys |
| 2: write and find | Quick notes grow into useful documents and remain easy to retrieve | Outline, find/replace, counts, consistent commands, ranked local search, note links, import/export fidelity |
| 3: everyday completeness | People can bring their existing material and keep using one app | Encrypted images/PDFs, complete attachment lifecycle, lightweight collections, large-library performance, polished output |
| 4: iOS extension | Native entry points extend a proven browser experience | Share extension, widgets, Shortcuts, protected device key storage, capture/scanning integrations; validate Capacitor/editor behavior before committing to a shell strategy |

Visual and accessibility improvements should accompany each release. Do not postpone them to a decorative final pass.

Defer public publishing, team collaboration, database builders, graph views, and cloud AI reflection until observed user demand justifies their complexity. The older roadmap's AI/reflection ideas should be revalidated against the current privacy and writing goals.

A credible first validation cohort is 8–12 target writers using their own material for several weeks, with explicit consent for any content-free diagnostics. Observe capture-to-save, finding an older note, longer writing, interruptions, migration, and restoration. Measure task success and repeated voluntary use; an aesthetic award is an external outcome, not a release criterion.
